Every `ChatClient` call you have made so far went through advisors, even when you registered none: Module 2's format text came
from `ChatModelCallAdvisor`, and `validateSchema()` added `StructuredOutputValidationAdvisor`. This lesson opens the chain itself:
the order advisors run in, what they can change, and the one advisor that makes part of the chain run more than once.

## 1. Spring mental model

Advisors are servlet filters for model calls. Each one gets the request, can change it, passes it on, and gets the response on the
way back.

| Spring you know | Spring AI 2.1 | In short |
| --- | --- | --- |
| `Filter` | `CallAdvisor` | Wraps the rest of the chain. Not calling `nextCall` stops the call. |
| `HandlerInterceptor` | `BaseAdvisor` | `before` and `after`, for both `call()` and `stream()`. |
| `@Order` | `getOrder()` | Lower runs first on the way in, last on the way out. |
| Request attributes | `request.context()` | A map for this call, filled by `.advisors(a -> a.param(...))`. |
| `request.mutate()` in WebFlux | `request.mutate()` | Requests and prompts are immutable, so you pass on a changed copy. |

The interfaces are small. `CallAdvisor.adviseCall(ChatClientRequest, CallAdvisorChain)` returns a `ChatClientResponse`.
`StreamAdvisor.adviseStream(ChatClientRequest, StreamAdvisorChain)` returns a `Flux` of them. Both extend `Advisor`, which adds
`getName()` and `getOrder()`. `ChatClientRequest` is a record of the `Prompt` and the context map; `ChatClientResponse` holds the
`ChatResponse` and the context.

These are the default orders in 2.1.0, read from the classes and from the chain a running `ChatClient` printed:

| Advisor | Order | Who adds it |
| --- | --- | --- |
| `SessionTurnAdvisor`, `VectorStoreChatMemoryAdvisor` | `HIGHEST_PRECEDENCE + 200` | You (the first through `SessionAdvisors`) |
| `ToolCallingAdvisor` | `HIGHEST_PRECEDENCE + 300` | `ChatClient`, on every client |
| `SessionMemoryAdvisor` | `HIGHEST_PRECEDENCE + 1000`, inside the tool loop | You, through `SessionAdvisors` |
| `SimpleLoggerAdvisor`, `SafeGuardAdvisor`, `QuestionAnswerAdvisor`, `RetrievalAugmentationAdvisor` | `0` | You |
| `StructuredOutputValidationAdvisor` | `LOWEST_PRECEDENCE - 2000` | `validateSchema()` |
| `ChatModelCallAdvisor` | `LOWEST_PRECEDENCE` | `ChatClient`, always last |

`ToolCallingAdvisor` deserves its own diagram. When the model asks for a tool, it runs the tool and calls the rest of the chain
again, so everything ordered after it runs once per model call. Advisors ordered before it run once per `ChatClient` call and see
the finished answer, with the token usage of every round added up.

Where memory sits is a choice. `SessionAdvisors` puts the memory advisor inside the loop by default, so it stores every tool
call and result and rebuilds each round's prompt from the session. This course orders it at `HIGHEST_PRECEDENCE + 210`, just
after the turn advisor and before the loop: it runs once per call, stores the question and the final answer, and the advisors
between it and the loop see the whole history. Module 4's RAG advisor needs exactly that.

Three more rules, all checked against the running code:

- **Equal orders.** `SimpleLoggerAdvisor`, `SafeGuardAdvisor` and the RAG advisors all default to `0`, and so does a custom
  advisor that returns 0. Before the tool loop, advisors with the same order run in reverse registration order. Inside it, which
  is where an order of `0` puts them with any real model, they run in registration order. Both are implementation details, not
  a contract.
- **Short-circuiting.** An advisor that returns a response without calling `nextCall` ends the call there. Nothing below it runs,
  including the model. `SafeGuardAdvisor` works this way.
- **Streaming.** `BaseAdvisor` runs `before` on `getScheduler()`, which defaults to `Schedulers.boundedElastic()`, and runs `after`
  only on the chunk that carries the finish reason. An advisor that implements only `CallAdvisor` is skipped by `stream()`.

Most custom advisors only need to change the request or the response, so extend `BaseAdvisor`. It works for both `call()` and
`stream()`. This one adds a language instruction to the system message when the caller passes a `Locale`:

<CodeFile title="src/main/java/com/example/support/chat/AnswerLanguageAdvisor.java">
```java {19,24,29}
package com.example.support.chat;

import java.util.Locale;

import org.springframework.ai.chat.client.ChatClientRequest;
import org.springframework.ai.chat.client.ChatClientResponse;
import org.springframework.ai.chat.client.advisor.api.AdvisorChain;
import org.springframework.ai.chat.client.advisor.api.BaseAdvisor;
import org.springframework.core.Ordered;

/** Tells the model which language to answer in, taken from a per-request advisor parameter. */
public final class AnswerLanguageAdvisor implements BaseAdvisor {

    public static final String LANGUAGE = "support.answer-language";

    @Override
    public int getOrder() {
        // After memory (+200) and before the tool loop (+300), so it runs once per call.
        return Ordered.HIGHEST_PRECEDENCE + 250;
    }

    @Override
    public ChatClientRequest before(ChatClientRequest request, AdvisorChain chain) {
        if (!(request.context().get(LANGUAGE) instanceof Locale locale)) {
            return request;
        }
        String instruction = "Answer in " + locale.getDisplayLanguage(Locale.ENGLISH) + ".";
        return request.mutate()
                .prompt(request.prompt().augmentSystemMessage(system -> system.mutate()
                        .text(system.getText().isEmpty() ? instruction : system.getText() + "\n" + instruction)
                        .build()))
                .build();
    }

    @Override
    public ChatClientResponse after(ChatClientResponse response, AdvisorChain chain) {
        return response;
    }
}
```
</CodeFile>

Register advisors once on the client. The comments record each order, so the chain can be read from the configuration:

<CodeFile title="src/main/java/com/example/support/chat/SupportChatConfig.java">
```java {19-23,32-35}
package com.example.support.chat;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor;
import org.springframework.ai.session.DefaultSessionService;
import org.springframework.ai.session.InMemorySessionRepository;
import org.springframework.ai.session.SessionService;
import org.springframework.ai.session.advisor.SessionAdvisors;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.Ordered;

@Configuration(proxyBeanMethods = false)
class SupportChatConfig {

    /** Conversations in memory for now; the Chat Memory lesson keeps them in PostgreSQL. */
    @Bean
    SessionService sessionService() {
        return DefaultSessionService.builder()
                .sessionRepository(InMemorySessionRepository.builder().build())
                .build();
    }

    @Bean
    ChatClient supportChatClient(ChatClient.Builder builder, SessionService sessionService) {
        return builder
                .defaultSystem("You are the support assistant for Acme Cloud.")
                .defaultAdvisors(
                        new AnswerLanguageAdvisor(),                          // HIGHEST_PRECEDENCE + 250
                        new SimpleLoggerAdvisor())                            // 0, in the tool loop
                // The turn (+ 200) and memory (+ 210) before the tool loop, so memory runs once per call.
                .defaultAdvisors(SessionAdvisors.builder(sessionService)
                        .memory(memory -> memory.order(Ordered.HIGHEST_PRECEDENCE + 210))
                        .build())
                .build();
    }
}
```
</CodeFile>

Pass the value for one call with `.advisors(advisor -> advisor.param(AnswerLanguageAdvisor.LANGUAGE, Locale.GERMAN))`. The
advisor reads it from `request.context()`.

An advisor is plain Java, so you can test it with a lambda as the `ChatModel` and look at the prompt that reached it:

<CodeFile title="src/test/java/com/example/support/chat/AnswerLanguageAdvisorTest.java">
```java {20,37}
package com.example.support.chat;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.ArrayList;
import java.util.List;
import java.util.Locale;

import org.junit.jupiter.api.Test;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.messages.AssistantMessage;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.ai.chat.model.Generation;
import org.springframework.ai.chat.prompt.Prompt;

class AnswerLanguageAdvisorTest {

    private final List<Prompt> prompts = new ArrayList<>();

    private final ChatClient chatClient = ChatClient.builder(prompt -> {
                prompts.add(prompt);
                return new ChatResponse(List.of(new Generation(new AssistantMessage("ok"))));
            })
            .defaultSystem("You are the support assistant for Acme Cloud.")
            .defaultAdvisors(new AnswerLanguageAdvisor())
            .build();

    @Test
    void addsTheLanguageToTheSystemMessage() {
        chatClient.prompt()
                .user("Where is my invoice?")
                .advisors(advisor -> advisor.param(AnswerLanguageAdvisor.LANGUAGE, Locale.GERMAN))
                .call()
                .content();

        assertThat(prompts.getLast().getSystemMessage().getText())
                .isEqualTo("You are the support assistant for Acme Cloud.\nAnswer in German.");
    }

    @Test
    void leavesThePromptAloneWithoutALanguage() {
        chatClient.prompt().user("Where is my invoice?").call().content();

        assertThat(prompts.getLast().getSystemMessage().getText())
                .isEqualTo("You are the support assistant for Acme Cloud.");
    }
}
```

## 4. Production gotchas & security

<Gotcha kind="reliability" title="Two advisors with the same order">
`SimpleLoggerAdvisor`, `SafeGuardAdvisor` and the RAG advisors all default to `0`. Whether a logger registered after RAG logs the
prompt with its documents depends on where the two sit: inside the tool loop the one registered first runs first, before it the
one registered last. Give every advisor its own order, and pass it to the builder (`.order(...)`) rather than relying on
registration order.
</Gotcha>

<Gotcha kind="cost" title="Advisors after ToolCallingAdvisor run on every model call">
A question that takes three rounds of tool calls makes four model calls, and every advisor ordered after
`HIGHEST_PRECEDENCE + 300` runs four times. For a logger that means four log entries; for `RetrievalAugmentationAdvisor` at its default order it means four
embeddings and four vector searches. Put an advisor that only needs the final answer before the tool loop.
</Gotcha>

<Gotcha kind="reliability" title="before() runs on another thread when streaming">
For `stream()`, `BaseAdvisor` moves `before` onto `Schedulers.boundedElastic()`. Thread-bound values such as the
`SecurityContext` or the logging MDC aren't there. Read the user and anything else you need in the controller and pass it as an
advisor parameter, as the lesson code does.
</Gotcha>

<Gotcha kind="reliability" title="after() doesn't see a whole streamed answer">
In a stream, `BaseAdvisor.after` runs once, on the chunk that carries the finish reason, and that chunk holds only the last
piece of text. An advisor that inspects the answer must implement `StreamAdvisor` itself and aggregate the chunks.
A `CallAdvisor` alone doesn't run for `stream()` at all.
</Gotcha>

<Gotcha kind="security" title="The context map travels with the request">
Everything you pass with `.param(...)` sits in `request.context()`, which every advisor can read and `SimpleLoggerAdvisor`
logs with the request. Pass identifiers, not secrets or tokens, and remember that a later advisor can't trust a value an earlier
one could have changed.
</Gotcha>

<Gotcha kind="migration" title="AdvisedRequest and aroundCall are gone">
Advisors written for the 1.0 milestones used `CallAroundAdvisor`, `AdvisedRequest` and `aroundCall(...)`. In 2.0 the types are
`CallAdvisor`, `ChatClientRequest` and `adviseCall(...)`, and the context is a plain `Map` on the request record. Port them by
building a changed request with `request.mutate()` and calling `chain.nextCall(...)`.
</Gotcha>

## Recap

- An advisor wraps the rest of the chain: `CallAdvisor` for `call()`, `StreamAdvisor` for `stream()`, `BaseAdvisor` for both
  through `before` and `after`.
- Lower `getOrder()` runs first on the way in. Built-ins sit at `+200` (the session turn), `+300` (tool calling), `+1000`
  (session memory, inside the loop), `0` (logging, guard, RAG) and `LOWEST_PRECEDENCE` (the model call). Give your advisors
  distinct orders.
- Advisors after `ToolCallingAdvisor` run once per model call; advisors before it run once and see the total usage.
- Requests are immutable: change them with `mutate()` and the prompt's `augmentUserMessage` and `augmentSystemMessage`, and pass
  per-call values through `.advisors(a -> a.param(...))`.
