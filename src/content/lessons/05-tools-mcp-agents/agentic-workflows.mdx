The assistant can look things up. Two jobs need more than one tool loop. A refund moves money, so the model must not be the one
who decides it. A support ticket with several questions needs several steps: split it, answer each part, merge the answers,
then check the result. This lesson builds both. Spring AI 2.0.2 has no workflow engine, and it doesn't need one: each step is a
`ChatClient` call, and plain Java connects the steps.

## 1. Spring mental model

Think of Spring Batch or Spring Integration. Your code defines the flow, and each step does one job. A **workflow** keeps the
control flow in code and asks the model to fill in each step. An **agent** lets the model choose the next step, which is what
the tool loop from lesson 1 does. Use a workflow when you know the steps. It is cheaper, it can be tested step by step, and it
can't wander.

| Pattern | What the code does | In this lesson |
| --- | --- | --- |
| Human in the loop | The model prepares an action; a person confirms it outside the model's loop | `proposeRefund`, then `POST /api/refunds/{id}/confirmation` |
| Orchestrator | One call plans the work as structured output | The planner returns a `Plan` with `entity(Plan.class)` |
| Routing | Code sends each input to a specialised client | One writer `ChatClient` per `Department` |
| Parallel workers | Independent calls run at the same time | Writers run on virtual threads |
| Evaluator-optimizer | A reviewer checks the result; an editor fixes it, up to a limit | `Review`, then a revision, at most `MAX_ROUNDS` times |

These rules come from the 2.0.2 classes and from tests we ran against them:

- `ToolCallingAdvisor.builder().toolExecutionEligibilityChecker(...)` can stop a tool from running and return the tool calls to
  the caller. But `MessageChatMemoryAdvisor` has already saved the assistant's tool call, with no tool result after it, so the
  conversation in memory is left with an unanswered call. That is why the refund is a proposal that the customer confirms in a
  separate request.
- `spring.ai.chat.client.tool-calling.enabled=false` stops `ChatClient` from registering `ToolCallingAdvisor`. The response then
  carries the tool calls, nothing runs them, and `ToolCallingManager.executeToolCalls(prompt, response)` is yours to call.
- `ChatClient.Builder.clone()` copies the auto-configured builder, so each role gets its own system prompt on the same model.
- A `ChatModel` called from virtual threads must be thread-safe. Our test model records prompts in a `CopyOnWriteArrayList` for
  that reason.

The repository binds each value itself, because the PostgreSQL driver can't infer a type for an enum or an `Instant`. We ran it
against PostgreSQL 17: `paramSource(refund)` fails with "Can't infer the SQL type". The conditional `UPDATE` is what makes a
confirmation happen once:

<CodeFile title="src/main/java/com/example/support/refund/RefundRepository.java">
```java {29,30,51}
package com.example.support.refund;

import java.time.ZoneOffset;
import java.util.List;
import java.util.Optional;
import java.util.UUID;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;

@Repository
public class RefundRepository {

    private final JdbcClient jdbc;

    RefundRepository(JdbcClient jdbc) {
        this.jdbc = jdbc;
    }

    public void insert(Refund refund) {
        jdbc.sql("""
                        INSERT INTO refunds (id, customer_id, order_number, amount, reason, status, expires_at)
                        VALUES (:id, :customerId, :orderNumber, :amount, :reason, :status, :expiresAt)""")
                .param("id", refund.id())
                .param("customerId", refund.customerId())
                .param("orderNumber", refund.orderNumber())
                .param("amount", refund.amount())
                .param("reason", refund.reason())
                .param("status", refund.status().name()) // the PostgreSQL driver can't bind an enum
                .param("expiresAt", refund.expiresAt().atOffset(ZoneOffset.UTC)) // nor an Instant
                .update();
    }

    public Optional<Refund> findForCustomer(String customerId, UUID id) {
        return jdbc.sql("SELECT * FROM refunds WHERE customer_id = :customerId AND id = :id")
                .param("customerId", customerId)
                .param("id", id)
                .query(Refund.class)
                .optional();
    }

    public List<Refund> findPendingForCustomer(String customerId) {
        return jdbc.sql("SELECT * FROM refunds WHERE customer_id = :customerId AND status = 'PENDING' ORDER BY expires_at")
                .param("customerId", customerId)
                .query(Refund.class)
                .list();
    }

    /** Moves a refund from PENDING to CONFIRMED. False when another request confirmed it first. */
    public boolean markConfirmed(UUID id) {
        return jdbc.sql("UPDATE refunds SET status = 'CONFIRMED' WHERE id = :id AND status = 'PENDING'")
                .param("id", id)
                .update() == 1;
    }
}
```

The service takes the amount from the order and pays only on confirmation. If the payment call throws, the transaction rolls
back and the refund is `PENDING` again, so the customer can retry with the same idempotency key:

<CodeFile title="src/main/java/com/example/support/refund/RefundService.java">
```java {46,60,63}
package com.example.support.refund;

import java.time.Clock;
import java.time.Duration;
import java.util.EnumSet;
import java.util.List;
import java.util.Set;
import java.util.UUID;

import com.example.support.order.Order;
import com.example.support.order.OrderRepository;
import com.example.support.order.OrderStatus;
import com.example.support.tools.ToolRefusalException;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/** The model can only propose a refund. Money moves when the customer confirms it, outside the model's loop. */
@Service
public class RefundService {

    static final Duration CONFIRMATION_WINDOW = Duration.ofMinutes(15);

    private static final Set<OrderStatus> REFUNDABLE = EnumSet.of(OrderStatus.SHIPPED, OrderStatus.DELIVERED);

    private final OrderRepository orders;
    private final RefundRepository refunds;
    private final PaymentClient payments;
    private final Clock clock;

    RefundService(OrderRepository orders, RefundRepository refunds, PaymentClient payments, Clock clock) {
        this.orders = orders;
        this.refunds = refunds;
        this.payments = payments;
        this.clock = clock;
    }

    @Transactional
    public Refund propose(String customerId, String orderNumber, String reason) {
        Order order = orders.findForCustomer(customerId, orderNumber)
                .orElseThrow(() -> new ToolRefusalException("This customer has no order " + orderNumber + "."));
        if (!REFUNDABLE.contains(order.status())) {
            throw new ToolRefusalException("Order " + orderNumber + " is " + order.status() + " and cannot be refunded.");
        }
        // The amount comes from the order, never from the model.
        Refund refund = new Refund(UUID.randomUUID(), customerId, orderNumber, order.total(), reason, RefundStatus.PENDING,
                clock.instant().plus(CONFIRMATION_WINDOW));
        refunds.insert(refund);
        return refund;
    }

    @Transactional(readOnly = true)
    public List<Refund> pending(String customerId) {
        return refunds.findPendingForCustomer(customerId);
    }

    @Transactional
    public Refund confirm(String customerId, UUID refundId) {
        Refund refund = refunds.findForCustomer(customerId, refundId).orElseThrow(() -> new RefundNotFoundException(refundId));
        if (clock.instant().isAfter(refund.expiresAt()) || !refunds.markConfirmed(refundId)) {
            throw new RefundNotConfirmableException(refundId);
        }
        payments.refund(refund.orderNumber(), refund.amount(), refund.id());
        return refund.confirmed();
    }
}
```

```java {30,32}
package com.example.support.refund;

import java.math.BigDecimal;
import java.security.Principal;
import java.time.Instant;
import java.util.List;
import java.util.UUID;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/refunds")
class RefundController {

    private final RefundService refunds;

    RefundController(RefundService refunds) {
        this.refunds = refunds;
    }

    @GetMapping("/pending")
    List<RefundResponse> pending(Principal principal) {
        return refunds.pending(principal.getName()).stream().map(RefundResponse::from).toList();
    }

    @PostMapping("/{refundId}/confirmation")
    RefundResponse confirm(@PathVariable UUID refundId, Principal principal) {
        return RefundResponse.from(refunds.confirm(principal.getName(), refundId));
    }

    record RefundResponse(UUID id, String orderNumber, BigDecimal amount, RefundStatus status, Instant expiresAt) {

        static RefundResponse from(Refund refund) {
            return new RefundResponse(refund.id(), refund.orderNumber(), refund.amount(), refund.status(), refund.expiresAt());
        }
    }
}
```

<CodeFile title="src/main/java/com/example/support/ticket/TicketReplyService.java">
```java {74,76,91,105}
package com.example.support.ticket;

import java.util.EnumSet;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.util.Assert;

/**
 * Three workflow patterns in one: a planner splits the ticket into issues (orchestrator), each issue goes to its
 * department's writer (routing) and the writers run in parallel (workers); then a reviewer sends the merged reply back
 * to the editor until it approves, at most {@value #MAX_ROUNDS} times (evaluator-optimizer). The code owns the control
 * flow; the model fills in each step.
 */
public class TicketReplyService {

    static final int MAX_ISSUES = 4;
    static final int MAX_ROUNDS = 3;

    private static final String ANSWER = """
            Answer only this part of the ticket: {question}

            The whole ticket, for context:
            {ticket}""";

    private static final String MERGE = """
            Merge these answers into one reply to the ticket, in the order given.

            Ticket:
            {ticket}

            Answers:
            {answers}""";

    private static final String REVIEW = """
            Ticket:
            {ticket}

            Draft reply:
            {reply}""";

    private static final String REVISE = """
            Rewrite this reply so that it fixes every problem listed.

            Ticket:
            {ticket}

            Reply:
            {reply}

            Problems:
            {problems}""";

    private final ChatClient planner;
    private final Map<Department, ChatClient> writers;
    private final ChatClient editor;
    private final ChatClient reviewer;

    TicketReplyService(ChatClient planner, Map<Department, ChatClient> writers, ChatClient editor, ChatClient reviewer) {
        Assert.isTrue(writers.keySet().containsAll(EnumSet.allOf(Department.class)), "Every department needs a writer");
        this.planner = planner;
        this.writers = Map.copyOf(writers);
        this.editor = editor;
        this.reviewer = reviewer;
    }

    public ReplyDraft draftReply(String subject, String body) {
        String ticket = "Subject: " + subject + "\n\n" + body;
        Plan plan = Objects.requireNonNull(planner.prompt().user(ticket).call().entity(Plan.class), "No plan");
        // The model decides how many workers run, so cap the fan-out.
        List<Issue> issues = plan.issues().stream().limit(MAX_ISSUES).toList();
        Assert.state(!issues.isEmpty(), "The planner found no issue in the ticket");

        List<String> answers = answerInParallel(ticket, issues);
        String reply = answers.size() == 1 ? answers.getFirst() : editor.prompt()
                .user(user -> user.text(MERGE).param("ticket", ticket).param("answers", String.join("\n\n---\n\n", answers)))
                .call()
                .content();

        for (int round = 1; ; round++) {
            String draft = reply;
            Review review = Objects.requireNonNull(reviewer.prompt()
                    .user(user -> user.text(REVIEW).param("ticket", ticket).param("reply", draft))
                    .call()
                    .entity(Review.class), "No review");
            if (review.approved() || round == MAX_ROUNDS) {
                return new ReplyDraft(issues.stream().map(Issue::department).distinct().toList(), draft, round, !review.approved());
            }
            reply = editor.prompt()
                    .user(user -> user.text(REVISE)
                            .param("ticket", ticket)
                            .param("reply", draft)
                            .param("problems", "- " + String.join("\n- ", review.problems())))
                    .call()
                    .content();
        }
    }

    private List<String> answerInParallel(String ticket, List<Issue> issues) {
        try (ExecutorService workers = Executors.newVirtualThreadPerTaskExecutor()) {
            List<CompletableFuture<String>> answers = issues.stream()
                    .map(issue -> CompletableFuture.supplyAsync(() -> writers.get(issue.department()).prompt()
                            .user(user -> user.text(ANSWER).param("question", issue.question()).param("ticket", ticket))
                            .call()
                            .content(), workers))
                    .toList();
            return answers.stream().map(CompletableFuture::join).toList();
        }
    }
}
```

## 4. Production gotchas & security

<Gotcha kind="security" title="The model never moves money">
A tool that refunds directly does so whenever the conversation makes it seem right, and the conversation includes whatever the
customer types. Let the tool create a proposal, take the amount from your own data, and move the money only when the signed-in
customer confirms it in a request the model can't make.
</Gotcha>

<Gotcha kind="reliability" title="Stopping a tool call inside the loop corrupts memory">
`toolExecutionEligibilityChecker` returns the tool calls to you without running them, but memory has already stored the
assistant's tool call, with no tool result after it. The next turn sends that unanswered call to the model. A pending action
that the customer confirms in its own request keeps the conversation clean.
</Gotcha>

<Gotcha kind="reliability" title="Confirm once, pay once">
Two clicks, a retry or two browser tabs can confirm the same refund at the same time. `UPDATE ... WHERE status = 'PENDING'`
lets one of them win, and the refund id as the provider's idempotency key covers a retry after the payment went through.
Return `404` for another customer's refund, so its existence isn't revealed.
</Gotcha>

<Gotcha kind="cost" title="Count the model calls">
A ticket with n issues costs one planner call, n writer calls, a merge when n is more than one, and up to `MAX_ROUNDS` reviews
with a revision between each pair. Two issues, approved in round 2, make seven calls. Cap the fan-out yourself, because the
planner decides how many issues there are, and give simple roles a cheaper model through their own builder.
</Gotcha>

<Gotcha kind="reliability" title="Every loop needs an exit">
A reviewer can keep finding problems. Fix the number of rounds and, when they run out, return the draft with a flag for a
person, as `needsAgent` does, instead of looping or failing the request.
</Gotcha>

<Gotcha kind="reliability" title="Parallel calls meet rate limits">
Virtual threads make fan-out cheap, but your provider limits requests and tokens per minute. Many tickets at once multiply the
calls. Keep the fan-out small and handle `429` responses with Spring AI's retry settings. A virtual thread also doesn't inherit
the request's `SecurityContext`, so pass a worker anything it needs as an argument.
</Gotcha>

<Gotcha kind="security" title="Drafts go to agents, not to customers">
The workflow writes text for a person to check before it is sent. Protect the endpoint with an agent scope, as
`SecurityConfig` does, and test that a customer's token gets `403`.
</Gotcha>

## Recap

- Workflows keep the control flow in code; agents let the model choose. Prefer a workflow when you know the steps.
- Actions with side effects are proposals. The customer confirms them in a separate request, with the amount taken from your
  own data, a conditional update and an idempotency key.
- Orchestrator, routing, parallel workers and evaluator-optimizer are plain Java around `ChatClient` calls: structured output for
  plans and reviews, `builder.clone()` per role and virtual threads for the fan-out.
- Cap the fan-out and the rounds, and hand what is left to a person.
