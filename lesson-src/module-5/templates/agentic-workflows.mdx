**You'll need:** the support app from the MCP lesson, structured output from Module 2, and Java's virtual threads.

A support ticket with several questions needs more than one tool loop. It needs several steps: split it, answer each part, merge
the answers, then check the result. This lesson builds that workflow. Spring AI 2.1.0 has no workflow engine, and it doesn't need
one: each step is a `ChatClient` call, and plain Java connects the steps.

## 1. Spring mental model

Think of Spring Batch or Spring Integration. Your code defines the flow, and each step does one job. A **workflow** keeps the
control flow in code and asks the model to fill in each step. An **agent** lets the model choose the next step, which is what
the tool loop from lesson 1 does. Use a workflow when you know the steps. It is cheaper, it can be tested step by step, and it
can't wander.

| Pattern | What the code does | In this lesson |
| --- | --- | --- |
| Orchestrator | One call plans the work as structured output | The planner returns a `Plan` with `entity(Plan.class)` |
| Routing | Code sends each input to a specialised client | One writer `ChatClient` per `Department` |
| Parallel workers | Independent calls run at the same time | Writers run on virtual threads |
| Evaluator-optimizer | A reviewer checks the result; an editor fixes it, up to a limit | `Review`, then a revision, at most `MAX_ROUNDS` times |

The previous lesson's refund is a fifth pattern, a human in the loop: the model asks for an action, and it runs only once a person confirms it.

These rules come from the 2.1.0 classes and from tests we ran against them:

- `ChatClient.Builder.clone()` copies the auto-configured builder, so each role gets its own system prompt on the same model.
- A `ChatModel` called from virtual threads must be thread-safe. Our test model records prompts in a `CopyOnWriteArrayList` for
  that reason.

Things to try:

- Pick **One issue**. No merge step runs, and the writer's answer goes straight to the reviewer.
- Pick **Two issues**. The billing writer promises a refund date, the reviewer catches it, and the editor revises the reply in
  round 2.
- Pick **Five issues**. The fifth issue is never sent, because the plan is capped at four. The reviewer keeps objecting, so
  after `MAX_ROUNDS` the draft goes to an agent with `needsAgent: true`. Lower `MAX_ROUNDS` and count the model calls.

## 4. Production gotchas & security

<Gotcha kind="cost" title="Count the model calls">
A ticket with n issues costs one planner call, n writer calls, a merge when n is more than one, and up to `MAX_ROUNDS` reviews
with a revision between each pair. Two issues, approved in round 2, make seven calls. Cap the fan-out yourself, because the
planner decides how many issues there are, and give simple roles a cheaper model through their own builder.
</Gotcha>

<Gotcha kind="reliability" title="Every loop needs an exit">
A reviewer can keep finding problems. Fix the number of rounds and, when they run out, return the draft with a flag for a
person, as `needsAgent` does, instead of looping or failing the request.
</Gotcha>

<Gotcha kind="security" title="Drafts go to agents, not to customers">
The workflow writes text for a person to check before it is sent. Protect the endpoint with an agent scope, as
`SecurityConfig` does, and test that a customer's token gets `403`.
</Gotcha>

<MoreGotchas>

<Gotcha kind="reliability" title="Parallel calls meet rate limits">
Virtual threads make fan-out cheap, but your provider limits requests and tokens per minute. Many tickets at once multiply the
calls. Keep the fan-out small and handle `429` responses with Spring AI's retry settings. A virtual thread also doesn't inherit
the request's `SecurityContext`, so pass a worker anything it needs as an argument.
</Gotcha>

</MoreGotchas>

## Recap

- Workflows keep the control flow in code; agents let the model choose. Prefer a workflow when you know the steps.
- Orchestrator, routing, parallel workers and evaluator-optimizer are plain Java around `ChatClient` calls: structured output for
  plans and reviews, `builder.clone()` per role and virtual threads for the fan-out.
- Cap the fan-out and the rounds, and hand what is left to a person.
